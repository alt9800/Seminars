## これまでの講義をふりかえる

- DEM（数値標高モデル）：建物や木を取り除いた「地面」の高さ
- DSM（数値表層モデル）：建物や木も含めた「表面」の高さ

これまでのゲスト講義では**[赤色立体地図](https://www.gsi.go.jp/bousaichiri/release_thematic_maps_20180606.html)**や**[Re:Earth Terrain](https://terrain.reearth.land)**が扱われていました。

## データどのように作られているか

- どちらもDEM（地面の高さのデータ）などをもとに計算して作られる
- DEMの多くは、航空機からレーザーを当てて地面を測る「航空レーザ測量」で作られている

### データの提供元
- 国土地理院：全国を対象にした「基盤地図情報（数値標高モデル）」
- 自治体：長野県・静岡県・岐阜県などが、県域のCS立体図や点群をG空間情報センターで公開

なお、5mメッシュには空中写真から作られたもの、10mメッシュには等高線から作られたものもある

## 2026年秋現在では全国の広い範囲で1m四方の解像度で高さデータが公開されている

参考URL:https://www.gsi.go.jp/common/000280733.pdf

- 国土地理院が2023年11月に「1mメッシュ（標高）」の提供を始めた

- 誰でも**無償**でダウンロードできる

※ 例えば、5mメッシュと比べて1mメッシュでは、同じ面積あたりの25倍の標高点を持つ精度です。

## 「メッシュ」とは何か

- 地面を同じ大きさのマス目（格子）に区切る
- マス目ひとつにつき、高さの値をひとつ持たせる
- マス目が細かいほど地形はなめらかになり、そのぶんデータは重くなる

→ デモ：dem-mesh-demo.html ( URLは /handson/demo/meshになるはず)

---

## データの便利な分け方 : 地域メッシュ

日本では、地図を緯度・経度で決まった区画に分けて番号を付けています（標準地域メッシュ）。

| 区画 | 大きさ（緯度×経度） | 1辺の目安 |
|---|---|---|
| 1次メッシュ | 40分 × 1度 | 約80km |
| 2次メッシュ | 5分 × 7分30秒（1次を8×8に分割） | 約10km |
| 3次メッシュ | 30秒 × 45秒（2次を10×10に分割） | 約1km |
| 4次メッシュ<br>2分の1地域メッシュ | 15秒 × 22.5秒（3次を2×2に分割） | 約500m |

- 「1mメッシュ」の「メッシュ」はマス目の大きさのこと
- 「3次メッシュ」の「メッシュ」は区画の単位のこと

## そもそも「高さ」とは何か

- 地球はでこぼこした楕円体に近い形をしている
- GNSS（GPSなど）で直接わかるのは「楕円体高」：数学的な楕円体からの高さ
- 私たちがふだん使う「標高」は、ジオイド（平均海面を陸の下まで延ばした面）からの高さ
- 標高 ＝ 楕円体高 − ジオイド高

ジオイドとは | 国土地理院
https://www.gsi.go.jp/buturisokuchi/grageo_geoid.html

## 「標高」の決め方 2025〜

これまで東京湾の平均海面を起点に、水準測量で全国へ高さを伝えてきたが、
距離が延びるほど誤差がたまり、地殻変動の影響も受ける問題を解消するため、
2025年4月から衛星測位と新しいジオイド・モデル「ジオイド2024日本とその周辺」で標高を決める仕組みに切り替わりました。
例えば富士山の三角点は 3775.51m → 3775.56m（5cm高くなった）

ジオイド・モデルのダウンロード（基盤地図情報ダウンロードサービス）
https://service.gsi.go.jp/kiban/app/geoid/

来たる、「ジオイド 2024 日本とその周辺」 正式版公開 - OPTiM TECH BLOG
https://tech-blog.optim.co.jp/entry/2025/03/26/100000

## [参考]基準点

測量の基準になるよう、位置や高さを正確に求めて地面に設置された点の総称が「基準点」です。

| 種類 | 主な役割 | 設置数の目安 |
|---|---|---|
| 三角点 | 緯度・経度・標高の基準| 約10万9千点 |
| 水準点 | 高さ（標高）の基準| 約1万8千点 |
| 電子基準点 | 衛星測位の電波を受けて、位置を連続で観測する | 約1,300点（約20km間隔） |

- 2025年4月の改定では、これらの基準点の標高の値がまとめて改定された

## 基盤地図情報の中身を見てみよう

- 国土地理院の「基盤地図情報ダウンロードサービス」から入手できる
- ファイル形式はXML（JPGIS/GML）
- 中身はほぼ「地表面,12.34」のような行がひたすら並んだもの
- データのない場所は -9999

## XMLのままでは地図ソフトで扱いにくい

- XML → GeoTIFF（画像の形をした標高データ）に変換する
- 変換ツールの例：QGISのプラグイン、国土地理院の変換ツール、GDAL
- GeoTIFFになれば、QGISで陰影図や等高線をすぐに作れる

## サンプルファイルの読み方表
余裕があれば東京都近辺のファイルに差し替えるかも

`FG-GML-5031-72-70-DEM1A-20251208.xml`
ダウンロードは2次メッシュ単位のzipで、中に3次メッシュのXMLがコレクションされています。

| 部分 | 意味 |
|---|---|
| `5031` | 1次メッシュ（約80km四方） |
| `72` | 2次メッシュ（約10km四方） |
| `70` | 3次メッシュ（約1km四方） |
| `DEM1A` | 1mメッシュ（標高） |
| `20251208` | データの作成日 |

## XMLの中身

```xml
<type>1mメッシュ（標高）</type>
<mesh>50317270</mesh>
<gml:Envelope srsName="fguuid:jgd2024.bl">
  <gml:lowerCorner>33.975 131.25</gml:lowerCorner>
  <gml:upperCorner>33.983333333 131.2625</gml:upperCorner>
</gml:Envelope>
<gml:GridEnvelope>
  <gml:low>0 0</gml:low>
  <gml:high>1124 749</gml:high>
</gml:GridEnvelope>
<gml:tupleList>
地表面,45.54
地表面,45.34
...
データなし,-9999.
</gml:tupleList>
<gml:sequenceRule order="+x-y">Linear</gml:sequenceRule>
<gml:startPoint>0 0</gml:startPoint>
```

## XMLの中身

- 範囲（Envelope）と格子の数（GridEnvelope）、高さの値の並び（tupleList）でできている
- 1ファイルに 1125 × 750 ＝ 84万3,750 マス分の高さが入る
- 値の種類：地表面、内水面（川や池）、データなし（-9999）

サンプルファイルは山口県宇部市であり、海が多くデータを欠損扱いにしある「マス」が多く含まれています。

## WebGIS「エンジン」いろいろ

| 名前 | 説明 |
|---|---|
| MapLibre GL JS | 平らな地図の上で地形を持ち上げて立体にする。日本のWeb地図で広く使われているOSS |
| deck.gl | 大量のデータを重ねて見せるのが得意なOSS。地形もレイヤーのひとつとして扱う |
| CesiumJS | 丸い地球の上に地形や3Dモデルを載せるOSS。PLATEAU VIEWの土台にもなっている |
| Navara | 地理の計算をする部分と描画する部分を分けた、新しい3D地図エンジン（OSS） |
| Google Maps Platform | Googleの地図サービス。3D地図や、実写の3D都市データも配信している |
| MachGL | Geoloniaが2026年11月に提供を始めた、軽さを重視した地図描画ライブラリ |
| 高徳地図 JS API | 中国の地図サービス。WebGLで描画し、3D表示もできる |
| mago3D | 韓国のGaia3Dが開発。現在は3Dデータや地形をWeb向けに変換するツールが中心 |

---

## 高さをWebでどのように表現するか

1. **画像の色で高さを表す**（標高PNG、Terrarium、Terrain-RGB）
   → MapLibre、deck.gl
2. **三角形をつなげた面で地面を表す**（quantized-mesh）
   → CesiumJS
3. **建物や地形を3Dモデルとして表す**（3D Tiles、Photorealistic 3D Tiles）
   → CesiumJS、Google、Navara

---

## 地球の丸さをどう表現しているか

- MapLibre：平らな地図（Webメルカトル）の上で、地形を上に持ち上げる
- CesiumJS / Navara：楕円体（丸い地球）の上に、地形や建物を置く

高さの基準面がそれぞれ違います。

見た目は両方地球儀にデータが張り付いている形ですが、3D表現における緯度経度高さをどう表すか、設計が異なる (e.g 3Dモデルにおける左手系右手系)


---

## 標高と楕円体高のちがい

- 日本のDEMの高さ：標高（ジオイドが基準）
- 3D地球儀エンジンの高さ：楕円体高（楕円体が基準）
- 日本付近では両者におおむね30〜40m程度の差がある
- 建物モデルを読み込んだときに、この差をそろえないと建物が浮いたり地面に沈んだりする

---

## エンジンごとの高さの扱い

| 名前 | 高さの基準 | 座標の持ち方 |
|---|---|---|
| MapLibre GL JS | 基準面を持たず、DEMの値をそのまま使う | Webメルカトルの x・y と、メートルから換算した z（y は南向き） |
| deck.gl | 海面からの高さ（メートル） | 内部で右手系の座標に変換 |
| CesiumJS | WGS84楕円体からの高さ（楕円体高） | 地球の中心を原点とする右手系の座標（ECEF） |
| Google Maps 3D | 平均海面（EGM96）からの高さ。地面や建物からの高さでも指定できる | 緯度・経度・高さで指定（内部は非公開） |

## いろいろな形式で表される標高

---

## 形式1：標高画像（Terrarium・Terrain-RGB・地理院標高PNG）

画素の色（R・G・B）に標高を詰め込んだ画像 として扱えます。

例えば富士山頂（3776m）の画素は形式によって以下のように格納されています。

| 形式 | 画素の色 (R, G, B) | 計算式 |
|---|---|---|
| Terrarium | (142, 192, 0) | R × 256 + G + B ÷ 256 − 32768 |
| Terrain-RGB | (2, 26, 32) | (R × 65536 + G × 256 + B) × 0.1 − 10000 |
| 地理院標高PNG | (5, 195, 0) | (R × 65536 + G × 256 + B) × 0.01 |

- 普通の地図タイルと同じ {z}/{x}/{y} の画像として扱える
- MapLibre GL JS と deck.gl は標準で読み、CesiumJS は変換すれば使える

---

## 形式2：quantized-mesh（三角形の面）

地形を三角形の面として持つ形式で、主に CesiumJS で採用されています。

```text
layer.json            … 全体の説明（タイルのURL・範囲・ズーム）
0/0/0.terrain         … タイル1枚分の面（バイナリ）
  ├ ヘッダー          … タイルの中心、最低と最高の高さ
  ├ 頂点              … 各頂点の位置 u・v と高さ（0〜32767 に詰めた値）
  └ 三角形            … どの3つの頂点を結ぶか
```

- 平らな場所は大きな三角形、起伏のある場所は細かい三角形にできる
- 高さはタイル内の最低〜最高を 0〜32767 に分けた値で持つ
- CesiumJS は標準で読みこむことが可能で、MapLibre GL JS はプラグインが存在している

---

## 形式3：3D Tiles（3Dモデル）

建物や地形の3Dモデルを細かさの段階ごとにタイルに分けた形式です。

```json
{
  "asset": { "version": "1.1" },
  "root": {
    "boundingVolume": { "region": [西, 南, 東, 北, 最低の高さ, 最高の高さ] },
    "geometricError": 100,
    "content": { "uri": "0/0/0.glb" },
    "children": [ … より細かいタイル … ]
  }
}
```

- tileset.json が全体の木構造で、各タイルの中身は glTF（.glb）などの3Dモデル
- 遠くでは粗いモデル、近づくと細かいモデルに切り替わる
- PLATEAU や Google の [Photorealistic 3D Tiles](https://developers.google.com/maps/documentation/tile/3d-tiles?hl=ja) がこの形式

## デモ：三つのエンジンで同じ富士山を見る

同じ地形（Mapterhorn）と同じ地点（富士山頂、3776m）を、三つのエンジンで表示する


```js
// deck.gl：DEM画像から面を組み立て、点を置く
new deck.TerrainLayer({ elevationData: url, elevationDecoder: terrarium });

```

## Mapterhorn：デモで使う地形データ

## Mapterhornについて

Mapterhornは世界中の地形をWeb地図用のタイルにして公開しているオープンデータです。全世界は[ESAのDEM（約30m）](https://portal.opentopography.org/raster?opentopoID=OTSDEM.032021.4326.3)を元にしていて、一部の国はより細かいDEMに置き換えられています。日本は国土地理院のDEM（1m・5m・10m）が元になっています。

データの形式は標高画像（Terrarium）で、デモでもこれを読み込んでいます。

出典表示：© Mapterhorn（https://mapterhorn.com/attribution）

---

## Terrarium形式について

Terrariumは、地図サービスのMapzenが公開していた地形タイルで使われていた形式です。Mapterhornもこの形式を引き継いでいます。

標高は次の式で画素の色に詰め込まれています。

h = R × 256 + G + B ÷ 256 − 32768

R と G で整数のメートルを表し、B で1m未満の端数（1/256 m 刻み）を表します。最後に32768を引くので、海面下の土地も表せます。富士山頂（3776m）なら (142, 192, 0) です。

MapLibre GL JS では `encoding: 'terrarium'` と書くだけで、この計算をエンジンが行います。

参考:https://protomaps.com/blog/mapterhorn-terrain/

---

MapterhornはPMTilesとして配布されています。
ただし、 MapLibre他ではtiles.mapterhorn.com/tilejson.json からタイル（{z}/{x}/{y}）として読み込んでいます。

---

## まとめ

- エンジンごとに、地球を平面として扱うか、球として扱うかの設計が違う
- 高さは「画像」「三角形の面（メッシュ）」「3Dモデル」のいずれかで表現される
- 経度・緯度・高さを渡せば、内部の座標への変換はエンジンが受け持つ
- ただし、データを重ねるときは高さの基準（標高か楕円体高か）を意識する

## 標高タイルについて (再掲)

Mapterhornから読み込まれるのは標高タイルです。
見た目は画像、中身は標高の数値をうまく格納してあります。


---

### 1. 陰影図と2.5D

- `hillshade`：標高から傾きを求め、光の当たり方で明暗を付ける
- `setTerrain`：地面そのものを標高の分だけ持ち上げる
- 陰影の計算は、表示のたびに GPU が行っている

→ ハンズオン step1.html

---

### Mapterhorn の配り方

- 世界中の標高データを1つの形式にまとめた公開タイル
- PMTiles（たくさんのタイルを1ファイルに詰めた形式）で配布
- ズーム12以下は全球のファイル、13以上は地域ごとのファイル
- `addProtocol` で、MapLibre が読めるように橋渡しする

---

### 2. 色を付ける、高さを強調する

- `color-relief`：標高の値ごとに色を決める（段彩）
- 色の割り当ても GPU が行う
- `exaggeration`：高さを何倍に見せるか
  - データは変わらない。見た目だけ

→ ハンズオン step2.html

---

### 3. 等高線を計算する

- MapLibre には等高線を作る機能がない
- maplibre-contour：標高タイルを読み、JavaScript で等高線を計算
- 計算した線を「ベクタタイル」として MapLibre に渡す
- ここだけ、計算するのは CPU

→ ハンズオン step3.html

## 4. 水を貯める

- クリックした地点の標高＋水深＝水面の高さ
- 水面より低く、つながっている場所を順に探す（塗りつぶし）
- 画像編集ソフトの「バケツ」と同じ考え方

→ ch3-navara.html タブ4（山頂の火口に貯める）

---

### 注意点

水を溜めているだけで今回は流してません。
1つの高さで水面を決めて、低い場所を満たしているだけです。
水が流れる速さ、時間の概念を導入すると地図に命が宿るかも！
流体の演算をする場合、格子ごとに水の動きを少しずつ進める演算を行うと良いでしょう。(WebGPU、GPGPUを使おう！)

---

## 5. ボールを転がす

- 標高の格子(地面に当たる部分)を物理エンジン（cannon-es）における「地面」として定義する
- ボール1個あたりが独立したインスタンス(プログラムコード状の実体として格納されている)、落ちる・ぶつかる・転がるを計算
- 計算するのは CPU（JavaScript）でOK!
- 数を増やすと顕著に重くなります。

## 地面よりも上にいろんなものを置いてみよう！

Web技術における3D表現としては建物であったり、立体物を配置することが簡単にできます。
また、様々な表現技法が一般化してきています。

e.g. DSM

---

## 1. 押し出し(Extrude)

地図上に表現される建物形状(フットプリント)を底面として、下からところてんのように押し出して建物を表現する技法は簡便に行うことができます。
(シンプルな形状から、『豆腐』と表現する人もいます。)

MapLibre では `fill-extrusion` という種類のレイヤーが用意されています。

OpenStreetMap には建物の高さや階数が登録されていることがあり、これを使うと手軽にフットプリントを押し出し処理することができます。

---

### 押し出しの得意なこと、苦手なこと

- 得意：簡単で軽い！色や高さを式で変えられる
- 苦手：屋根の形や複雑な形状の立体物
- 高さが登録されていない建物には一律して仮の値を与えることが多い。

---

## 2. GLB：3Dの形をそのまま地図上に置きたい！

glTF は Khronos Group が決めた3Dモデルの形式です。GLB はそれを1つのファイルにまとめたものです。形・色・テクスチャ・アニメーションを1つのファイルに入れられます。

地図専用の形式ではないので、ゲームエンジンやARなど地図以外でも使えます。Webで3Dを扱うなら、まずGLBを選ぶのが簡単です。

---

## GLBを地図に置く

MapLibre はGLBを直接は読めないので、3D描画ライブラリの three.js を地図に重ねて描きます。(ちょうど前章のNavaraで使ったアイディアと同様のものですね。)

GLBの中には**緯度経度**が入っていません。どこに、どの向きで、どの大きさで置くかは、コードとして設定する必要があります。(もちろん変数としてインタラクティブに変えられるようにしてもいいでしょう。)


---

## 3. 3D Tiles：位置を持った3Dデータ

前々章の復習ですが、全体の目次として `tileset.json` がglbをコレクションしてまとめてくれている形式です。
「glbとともに地理空間上の`メタデータ`を持っている」状態だと言えます。

範囲が広くても、見えている場所の分だけを、遠くは粗く近くは細かく読み込みます。
(漸進的読み込み、遅延読み込み、というような専門用語(?)もあります)

PLATEAUの建物も3D Tilesで公開されています。


---

### 建物が浮いている？

地形データと建物データの基準となる標高を合わせないと建物が宙に浮いたり、あるいは埋まることもあります。
地下を表現したい際は意図的に「埋める」こともあります。

(この講義の前々回のRe:Earthの回でも述べられていました。)

---

## 4. 点群(Point Cloud)

レーザ測量や写真測量で得た、位置と色を持つ点の集まりです。点の間隔はばらばらで、レーザーがセンサーに跳ね返って記録された地面、木や壁などが表現されます。

(小さい規模であれば iPhone 12 Pro以降のLiDARセンサーでも簡単に取得が可能です)

DSMモデルから地表以外の点群を間引くとDEMになるのでした。

---

## 5. Gaussian Splatting

見た方向から見た目を(ガウス楕円体で)再現する技術です。

色・透明度・広がりを持つ粒を大量に重ねて、写真に近い見た目を作ります。

2026年には Splat を glTF に入れる拡張（KHR_gaussian_splatting）が策定されました。GLBの中にSplatを入れ、3D Tilesとして地図に置くことができます。(技術的には...)

細かい見た目(植物の葉の鋸歯など)や透明、黒など光学特性で点群が取得しにくいモノの見た目を再現することもできます。
メッシュ化(当たり判定を策定すること)がかなり難しいです。

e.g. NeRF、フォトグラメトリ
